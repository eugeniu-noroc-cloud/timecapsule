# ADR-0002. Размещение базы данных в приватной подсети

**Статус:** принято
**Дата:** 2026-10-28

## Контекст

В ЛР2 приложение TimeCapsule и PostgreSQL работали на одном экземпляре EC2 в default VPC, где все подсети публичные. База была доступна только на localhost, но жила на сервере, открытом в интернет, и разделяла с приложением процессор, память и диск.

В ЛР3 построена собственная сеть `timecapsule-dev-vpc` (10.28.0.0/16) с публичными и приватными подсетями в двух зонах доступности (eu-north-1a, eu-north-1b). Нужно решить, где размещать базу данных.

Ограничения:
- учебный проект, один разработчик, бюджет — бесплатный план и минимальные расходы;
- управляемые базы (Amazon RDS) ещё не изучены, база ставится на EC2 вручную;
- базе нужны обновления безопасности из интернета;
- SSH-доступ к серверам должен идти только через один сервер (bastion).

## Решение

База данных размещается на отдельном экземпляре `timecapsule-dev-db` в приватной подсети `timecapsule-dev-private-a` (10.28.10.0/24):

- у сервера нет публичного адреса, а в таблице `timecapsule-dev-private-rt` нет маршрута в интернет;
- Security Group `timecapsule-dev-db-sg` пропускает порт 5432 только от `timecapsule-dev-web-sg`, а SSH — только от `timecapsule-dev-bastion-sg`;
- `pg_hba.conf` пускает только пользователя `timecapsule` в базу `timecapsule` из подсети public-a с паролем (scram-sha-256);
- приложение находит базу по имени `db.timecapsule.internal` из приватной зоны Route 53, а не по IP;
- для обновлений пакетов временно создаётся NAT Gateway, который удаляется сразу после установки.

## Рассмотренные альтернативы

**1. База на одном сервере с приложением (как в ЛР2).**
Самый простой и дешёвый вариант: один сервер, подключение через localhost, никаких сетевых правил. Отклонён: база находится на сервере, открытом в интернет, и взлом приложения сразу даёт доступ к файлам базы. Приложение и база конкурируют за ресурсы одного t3.micro, их нельзя масштабировать и обновлять по отдельности, а отказ сервера останавливает всё сразу.

**2. Отдельный сервер базы в публичной подсети.**
База отделена от приложения, сервер сам получает обновления через Internet Gateway, NAT не нужен. Отклонён: у сервера есть публичный адрес и маршрут в интернет, поэтому доступ к базе держится только на Security Group и пароле. Одна ошибка в правиле (например, 5432 открыт для 0.0.0.0/0) делает базу видимой всему интернету, а такие порты постоянно сканируют боты.

**3. Отдельный сервер базы в приватной подсети (выбран).**
Из интернета до базы нет пути на уровне маршрутизации: нет публичного адреса и нет маршрута через Internet Gateway. Поверх этого работают Security Group и pg_hba.conf, то есть защита эшелонированная: ошибка в одном слое не открывает базу. Цена — сложнее администрирование (SSH через bastion) и обновления (нужен NAT).

## Последствия

**Лучше:**
- база недоступна из интернета даже при ошибке в Security Group;
- приложение и база разделены: их можно останавливать, обновлять и масштабировать независимо, отказ базы не уничтожает сервер приложения (проверено в задании 13: после перезапуска db-server приложение восстановилось без изменений);
- благодаря имени `db.timecapsule.internal` пересоздание db-server требует правки только одной DNS-записи, а не `.env` на всех серверах приложения.

**Обновления базы без постоянного выхода в интернет.**
Для `dnf update` временно создаётся NAT Gateway в public-a с Elastic IP и маршрут `0.0.0.0/0` в private-rt; после установки шлюз, маршрут и адрес удаляются. Такой сеанс длится минуты и стоит несколько центов (≈ $0,05 в час за шлюз плюс трафик), тогда как постоянный NAT Gateway стоил бы около $1,25 в сутки, то есть ≈ $37 в месяц — больше, чем все остальные ресурсы проекта вместе. Минус: обновления не ставятся автоматически, процедуру нужно не забывать выполнять, а после неё — не забывать удалить шлюз.

**Elastic IP у app-server и балансировщик нагрузки.**
Пользователи обращаются к app-server по адресу, который записан в `APP_URL`, поэтому ему выдан постоянный Elastic IP `timecapsule-dev-app-eip` (≈ $3,6 в месяц, оплачивается даже у остановленного сервера). Когда перед приложением появится балансировщик нагрузки, пользователи будут обращаться к его DNS-имени, а серверы приложения смогут переехать в приватные подсети без публичных адресов — Elastic IP станет не нужен и его можно будет освободить.

**Хуже / риски:**
- добавились два сервера (bastion и db), а с ними расходы на диски и администрирование;
- SSH на app-server и db-server идёт только через bastion: если bastion недоступен или изменился его адрес, администрировать серверы нельзя;
- база и приложение по-прежнему в одной зоне eu-north-1a: отказ зоны остановит приложение. Подсеть private-b пока не используется;
- загруженные файлы остались на диске app-server (storage/uploads) и пропадут вместе с ним.

**Дальнейшее развитие:** перенести базу в Amazon RDS (Multi-AZ, автоматические обновления и резервные копии), файлы — в S3, а перед несколькими серверами приложения поставить балансировщик нагрузки.
