# ADR-0001. Доставка кода на сервер через git pull, выполняемый вручную

**Статус:** принято
**Дата:** 2026-10-22

## Контекст

Приложение TimeCapsule (PHP, PostgreSQL) работает на одном экземпляре EC2 (t3.micro, Amazon Linux 2023, регион eu-north-1). Код хранится в публичном репозитории `eugeniu-noroc-cloud/timecapsule` на GitHub. Нужно выбрать, как новая версия кода попадает на сервер.

Ограничения:
- один сервер, один разработчик, учебный проект;
- нет CI/CD и платных инструментов, доступны только git и SSH;
- по специальности Informatică aplicată предусмотрен вариант A — выполнение команд деплоя вручную;
- секреты (`.env`) не должны попадать в репозиторий;
- после обновления кода нужно также обновить зависимости Composer и структуру базы данных.

## Решение

Новая версия выпускается так: изменения отправляются в репозиторий командой `git push`, затем на сервере по SSH вручную выполняется последовательность команд:

```bash
cd /var/www/timecapsule
git pull
composer install --no-dev --optimize-autoloader
php bin/init-db.php
sudo systemctl reload php-fpm
```

Единственный источник кода — репозиторий на GitHub. Сервер только читает его по HTTPS и не имеет прав на запись. Исправления на сервере напрямую не вносятся, откат выполняется через `git revert` в репозитории и повторный деплой.

## Рассмотренные альтернативы

**1. Копирование файлов через scp.**
Самый простой способ, применённый в Части 1 для статического сайта. Отклонён: на сервере неизвестно, какая версия кода работает; легко забыть скопировать один из файлов; нет истории изменений и нормального отката; код существует только на компьютере разработчика.

**2. git pull вручную на сервере (выбран).**
Версия на сервере всегда соответствует конкретному коммиту, откат делается через репозиторий, история изменений сохраняется. Недостаток: команды нужно помнить и вводить руками каждый раз, легко пропустить шаг (например, `composer install`).

**3. Скрипт deploy.sh, запускаемый одной командой по SSH.**
Те же шаги, что в варианте 2, но записанные в скрипт с `set -euo pipefail`: скрипт останавливается при первой ошибке, печатает каждый шаг и итоговый коммит. Деплой можно запустить со своего компьютера одной командой `ssh ... ./deploy.sh`. Технически это лучший из трёх вариантов, но для специальности Informatică aplicată в работе предусмотрен вариант A; скрипт — естественный следующий шаг развития выбранного решения.

## Последствия

**Лучше:**
- код на сервере всегда соответствует коммиту в репозитории, его видно командой `git log -1`;
- откат прозрачен и сохраняется в истории (`git revert`);
- сервер не может изменить код в репозитории, даже если его взломают;
- секреты хранятся только в `.env` на сервере и защищены `.gitignore`.

**Хуже / риски:**
- деплой зависит от человека: шаги можно перепутать или пропустить;
- во время `git pull` сайт кратко работает на смеси старых и новых файлов;
- нет проверок перед деплоем: синтаксическая ошибка попала на сервер, и сайт был недоступен около 2,5 минут;
- проверка `/health` не обнаруживает ошибки в шаблонах страниц;
- нет автоматического отката, уведомлений и журнала выпусков.

**Дальнейшее развитие:** перейти на `deploy.sh`, затем на CI/CD (например, GitHub Actions) с проверкой кода (`php -l`, тесты) до деплоя и smoke-тестом главной страницы после него.
